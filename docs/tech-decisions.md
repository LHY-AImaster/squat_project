# 🧠 Tech Decisions

본 문서는 SquatMate 개발 과정에서 마주한 주요 기술적 문제와 이를 해결하기 위해 내린 설계 및 구현상의 의사결정을 설명합니다.

## 1. 앱 중심의 실시간 스쿼트 분석

SquatMate는 블루투스로 수신한 센서 데이터의 각도 계산과 스쿼트 동작 판정을 Flutter 앱에서 처리하도록 설계했습니다. 센서 데이터는 짧은 간격으로 지속해서 수신되기 때문에, 매 데이터마다 서버에 요청을 보내는 방식은 불필요한 통신을 증가시키고 실시간 응답에도 영향을 줄 수 있다고 판단했습니다.

이에 따라 센서 데이터 수신부터 각도 계산, 스쿼트 횟수 및 자세 오류 판정까지의 과정을 앱에서 수행하도록 구성했습니다. 서버는 운동 기록 저장과 AI 코칭 등 별도의 역할을 담당하도록 분리했습니다.

이러한 구조를 통해 실시간 운동 측정과 서버 통신 간의 의존성을 줄이고자 했습니다. 다만 실제 운동 기록의 서버 동기화와 AI 코칭 등 일부 기능은 서버 연결이 필요하므로, 앱의 모든 기능이 오프라인에서 동작하는 것은 아닙니다.

## 2. 로컬 기록과 서버 기록의 분리

운동 기록에는 사용자의 신체 활동 정보가 포함되므로, 기록을 서버에 바로 전송하기보다 기기에 먼저 저장하고 사용자가 전송 여부를 결정할 수 있도록 설계했습니다.

앱에서는 SQLite를 활용해 운동 기록을 로컬에 저장하고, 사용자가 선택한 기록만 서버로 전송합니다. 이를 통해 서버에 전송할 기록을 사용자가 직접 관리할 수 있도록 했습니다.

서버 전송에 성공한 기록은 동기화 상태를 갱신하고, 전송에 실패한 기록은 미동기화 상태로 유지합니다. 따라서 네트워크 오류 등으로 전송이 실패하더라도 로컬에 저장된 기록을 유지하고 이후 다시 전송할 수 있습니다.

## 3. 독립적인 자세 오류 판정 구조

초기에는 하나의 스쿼트 동작에서 발생할 수 있는 여러 자세 오류를 판정하는 로직이 서로 복잡하게 연결되어 있었습니다. 하강과 상승 과정을 세분화하고 각 과정에서 발생한 오류를 구분하는 방식은 조건과 예외 상황을 늘려 구현 및 유지보수를 어렵게 만들었습니다.

이를 개선하기 위해 각 오류 조건을 독립적으로 검사하는 방식으로 판정 구조를 단순화했습니다. 한 번의 스쿼트 동작에서 허리 각도, 최대 허벅지 각도, 수행 시간을 각각 평가하도록 구성했습니다.

이러한 구조를 통해 여러 오류 조건이 동시에 충족되더라도 각 오류를 유형별로 구분해 집계할 수 있습니다. 또한 오류 판정 조건을 개별적으로 수정하거나 추가하기 쉬워져 전체 판정 로직의 복잡성을 줄일 수 있었습니다.

## 4. EMA 기반 로우패스 필터를 활용한 센서 노이즈 완화

SquatMate는 허리와 허벅지 센서에서 수신한 가속도 벡터를 이용해 상대 각도를 계산하고, 이를 바탕으로 스쿼트 깊이와 자세 오류를 판정합니다.

초기 구현에서는 별도의 필터링 없이 계산된 각도를 사용했습니다. 그러나 센서가 정지한 상태에서도 각도 값이 미세하게 흔들렸으며, 이로 인해 스쿼트 깊이를 잘못 판정하거나 자세 오류가 발생하는 문제가 있었습니다. 실시간 각도 UI 역시 불안정하게 표시되었습니다.

이러한 문제를 완화하기 위해 계산된 상대 각도에 EMA(Exponential Moving Average, 지수이동평균) 기반 로우패스 필터를 적용했습니다. 필터 계수는 0.15이며, 이전 필터링 값에 85%, 현재 측정된 각도에 15%의 가중치를 적용합니다.

```text
Filtered_t = 0.85 × Filtered_(t-1) + 0.15 × Raw_t
```

필터 적용의 목적은 순간적인 센서 노이즈로 인한 각도 변동을 줄여 각도 표시와 스쿼트 판정에 사용되는 값을 안정화하는 것입니다. 실제 테스트에서도 필터 적용 후 불필요한 오류 판정이 줄어드는 것을 확인했습니다.

다만 필터링은 각도 변화에 대한 반응을 늦출 수 있으므로, 빠른 동작에서는 실제 최대 각도를 충분히 반영하지 못할 가능성이 있습니다. 이를 고려해 한 회 수행 시간이 3초 미만인 경우 빠른 수행 오류로 분류하도록 구성했습니다. 이는 적절한 운동 속도를 유도하기 위한 별도의 판정 조건이며, 필터링으로 인한 반응 지연 자체를 보정하는 기능은 아닙니다.

## 5. 기준 벡터 재설정 기능

하드웨어 프로토타입을 착용하고 테스트하는 과정에서 허리와 허벅지 센서의 부착 위치와 각도를 매번 동일하게 유지하기 어렵다는 점을 확인했습니다. 센서의 착용 상태가 달라지면 초기 기준 벡터에도 차이가 발생하며, 이는 상대 각도 계산과 스쿼트 판정에 영향을 줄 수 있습니다.

이를 보완하기 위해 앱에서 기준 벡터를 다시 설정할 수 있도록 구현했습니다. 운동 시작 또는 초기화 과정에서 영점을 설정하고, 사용자는 이 과정에서 똑바로 선 자세를 유지해야 합니다. 영점 설정 안내가 끝나고 운동 시작 안내가 표시되면 측정을 시작할 수 있습니다.

이 기능은 센서 부착 상태를 항상 동일하게 유지하기 어려운 초기 하드웨어 프로토타입의 한계를 보완하기 위한 설계입니다. 기준 벡터를 재설정하더라도 센서 부착 오차 자체가 사라지는 것은 아니지만, 매번 달라질 수 있는 착용 상태를 측정 기준에 반영할 수 있습니다.

## 6. PostgreSQL로 데이터베이스 통합

초기 개발 단계에서는 로컬 환경에서 MariaDB를 사용하고, 온라인 배포 환경에서는 PostgreSQL을 사용했습니다. 그러나 개발 환경과 배포 환경에서 서로 다른 데이터베이스 엔진을 사용하면 설정과 테스트 과정에서 차이가 발생하고, 환경별 문제를 관리하기 어려워질 수 있었습니다.

이를 줄이기 위해 로컬과 배포 환경의 데이터베이스를 PostgreSQL로 통합했습니다. 두 환경에서 동일한 데이터베이스 엔진을 사용함으로써 개발 및 테스트 환경의 차이를 줄이고, 배포 환경과 일관된 기준으로 서버를 개발할 수 있도록 했습니다.

데이터베이스 엔진을 통일했다고 해서 로컬 데이터와 배포 데이터가 자동으로 공유되는 것은 아닙니다. 각 환경은 서로 다른 접속 정보와 데이터베이스를 사용하며, 접속 정보 역시 환경에 맞게 별도로 관리합니다.

## 7. 단일 AI 코칭 결과 캐싱

Gemini API를 활용한 AI 코칭 기능에서는 불필요한 중복 호출을 줄이고 API 사용량을 효율적으로 관리하는 것이 중요했습니다. 이를 위해 단일 운동 기록에 대한 코칭 결과를 서버 데이터베이스에 함께 저장하도록 구현했습니다.

코칭을 요청할 때 해당 운동 기록에 대한 기존 결과가 존재하면 저장된 결과를 재사용하고, 결과가 없는 경우에만 Gemini API를 호출합니다. 이러한 방식은 동일한 운동 기록에 대한 반복적인 API 호출을 줄이고, 기존에 생성된 코칭 결과를 일관되게 제공할 수 있도록 했습니다.

반면 여러 운동 기록을 선택해 생성하는 종합 코칭 결과는 별도로 저장하지 않습니다. 종합 코칭은 선택한 기록들의 통계를 바탕으로 생성되기 때문에 기록 조합에 따라 결과가 달라질 수 있습니다. 현재는 이러한 조합별 결과를 별도로 저장하고 관리하는 복잡성을 줄이는 방향을 선택했으며, 동일한 조건으로 다시 요청하더라도 AI API가 재호출될 수 있습니다.
