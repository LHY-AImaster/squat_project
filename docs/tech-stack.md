# 🛠 Tech Stack

본 문서는 SquatMate 개발에 사용된 주요 기술 스택과 각 기술을 선정한 배경 및 이유를 설명합니다.

| 구분 | 기술 | 선정 이유 |
|---|---|---|
| 모바일 앱 | Flutter · Dart | 하나의 코드베이스로 Android와 iOS를 고려한 크로스플랫폼 개발 |
| 백엔드 | Java 21 · Spring Boot | 산업 현장에서 활용되는 백엔드 기술을 경험하고, 체계적인 서버 구조와 유지보수 방식 학습 |
| 데이터베이스 | PostgreSQL | Supabase 배포 환경에 맞춰 기존 MariaDB에서 전환하고 온라인 데이터 관리 |
| 로컬 저장소 | SQLite | 운동 기록을 기기에 먼저 저장하고, 사용자가 서버 전송 여부를 직접 결정하는 로컬 우선 구조 구현 |
| 인증 | JWT | 토큰 기반 인증을 통해 앱과 서버 간 사용자 식별 및 분산된 환경에서의 독립적인 인증 처리 |
| AI 코칭 | Gemini API | 무료 사용량과 프로젝트에 필요한 수준의 문장 생성 성능을 고려한 비용 효율적인 AI 연동 |
| 배포 | Render · Supabase | GitHub 연동을 통한 간편한 서버 배포와 별도 PostgreSQL 호스팅을 통한 운영 비용 절감 |

## Flutter · Dart

**Cross-platform Mobile Development**

Android와 iOS를 함께 고려한 모바일 앱 개발을 위해 Flutter를 선택했습니다. 하나의 코드베이스로 두 플랫폼의 앱을 개발할 수 있으며, SquatMate에 필요한 UI 구성, BLE 센서 연동, 실시간 데이터 처리 및 상태 관리 기능을 구현하기에 충분하다고 판단했습니다.

## Java · Spring Boot

**Structured Backend Development**

실제 기업 환경에서 널리 활용되는 기술을 바탕으로 서버 개발과 운영 경험을 쌓고자 Java와 Spring Boot를 선택했습니다. 사용자 인증, 운동 기록 관리, 데이터베이스 연동 및 외부 API 통합 등 다양한 기능을 체계적으로 구성하고 유지보수하는 것을 목표로 했습니다.

- **실무 기술 경험:** 산업 현장에서 활용되는 백엔드 기술 생태계 경험
- **구조화된 설계:** 의존성 주입과 데이터 접근 기술을 통한 역할별 구성
- **유지보수 및 운영:** 보안, 트랜잭션, 테스트 등 서버 개발을 지원하는 생태계

프로젝트 규모만 고려하면 FastAPI와 같은 가벼운 프레임워크도 충분히 활용할 수 있습니다. 하지만 이번 프로젝트에서는 구현의 간결함보다 서버 구조와 유지보수 방식을 경험하는 데 더 큰 의미를 두었습니다.

## MariaDB → PostgreSQL

**Database Migration for Deployment**

초기 개발 단계에서는 학교에서 학습한 경험과 익숙한 개발 환경을 바탕으로 MariaDB를 선택했습니다. 사용자 정보와 운동 기록을 관리하는 프로젝트의 초기 요구사항을 충족하기에 충분하다고 판단했습니다.

온라인 배포 환경을 구성하는 과정에서 Supabase가 PostgreSQL 기반의 데이터베이스를 제공한다는 점을 고려해 PostgreSQL로 전환했습니다. 두 데이터베이스 모두 관계형 데이터베이스이므로, 기존 사용자 관리와 운동 기록 저장 등 핵심적인 서버 기능을 유지하면서 전환을 진행할 수 있었습니다.

이번 전환은 특정 데이터베이스가 다른 데이터베이스보다 절대적으로 우수하다는 판단보다는, 실제 배포 환경과 개발 편의성, 기존 시스템에 미치는 변경 범위를 함께 고려한 결정이었습니다.

## SQLite

**Local-first Record Management**

운동 기록을 서버에 바로 전송하기보다 사용자 기기 내부에 먼저 저장하고 관리하기 위해 SQLite를 선택했습니다. SQLite는 별도의 데이터베이스 서버 없이 앱 내부에서 사용할 수 있는 경량 관계형 데이터베이스로, 모바일 환경의 로컬 저장소로 활용하기에 적합했습니다.

또한 서버에서 사용하는 PostgreSQL과 동일한 관계형 데이터베이스라는 점에서 테이블과 SQL을 기반으로 한 데이터 관리 개념을 일관되게 유지할 수 있었습니다. 이를 바탕으로 앱 내부의 1차 저장소와 서버의 PostgreSQL을 활용한 2단계 저장 구조를 설계하고, 사용자가 자신의 운동 기록을 서버에 전송할지 직접 결정할 수 있도록 했습니다.

## JWT

**Token-based Authentication**

사용자 비밀번호 보호를 시작으로 서버의 보안 구조를 확장하는 과정에서 JWT 기반 인증 방식을 도입했습니다. Flutter 앱과 Spring Boot 서버가 분리된 구조에서 로그인 이후에도 사용자를 식별하고 API 요청을 검증할 수 있도록 토큰을 활용했습니다.

JWT는 웹과 모바일 서비스에서 널리 활용되는 토큰 기반 인증 방식입니다. 이번 프로젝트에서는 토큰 발급과 검증을 비롯해 인증된 사용자의 접근 권한 확인, 폐기 토큰을 활용한 로그아웃 처리까지 서버의 인증 및 보안 구조를 직접 구현하고자 했습니다.

## Gemini API

**Cost-effective AI Integration**

AI 코칭 기능을 구현하기 위해 외부 생성형 AI API를 검토했으며, 비용 부담을 최소화하는 것을 가장 중요한 선정 기준으로 삼았습니다. 특히 SquatMate의 AI 기능은 방대한 데이터를 분석하거나 복잡한 연산을 수행하기보다, 앱에서 수집한 운동 기록과 오류 정보를 바탕으로 사용자가 자신의 문제점을 이해하고 개선 방향을 떠올릴 수 있도록 돕는 역할에 초점을 두었습니다. 따라서 고성능 유료 모델을 도입할 필요성은 크지 않다고 판단했습니다.

Gemini API는 무료 사용량을 제공하면서도 이러한 수준의 문장 생성 및 정보 전달 기능을 구현하기에 적합했습니다. 이를 통해 별도의 API 비용 부담 없이 AI 코칭 기능을 개발하고 테스트할 수 있었습니다.

## Render · Supabase

**Cost-effective Cloud Deployment**

온라인 서비스를 운영하기 위해서는 서버와 데이터베이스를 외부에서 접근할 수 있는 환경에 배포해야 했습니다. 학생 프로젝트 특성상 운영 비용을 최소화하는 것을 우선적으로 고려했으며, GitHub와 연동해 Spring Boot 서버를 간편하게 배포할 수 있는 Render를 선택했습니다.

데이터베이스는 Render에서 함께 운영할 경우 발생하는 비용을 고려해 별도의 호스팅 서비스를 검토했고, 무료 사용량을 제공하는 Supabase를 선택했습니다. 이 과정에서 PostgreSQL 기반의 온라인 데이터베이스 환경을 구성하면서 기존 MariaDB를 PostgreSQL로 전환했습니다.

각 서비스의 기능뿐 아니라 비용, 배포 편의성, 기존 시스템과의 호환성을 함께 고려해 서버와 데이터베이스를 분리하여 운영하는 구조를 구성했습니다.
